# AI 多模型聊天室 MVP 规范

## 1. 项目定位

本项目用于构建一个面向个人使用的 AI 多模型聊天室 Web 应用。

第一阶段目标不是做完整产品，而是尽快交付一个最基础、可运行、可演示的 MVP，用来验证多模型协作聊天的核心链路是否成立。

本阶段只验证以下 4 件事：

1. 能配置模型
2. 能单聊
3. 能多模型按顺序回复
4. 能保存聊天记录并重新打开继续聊天

## 2. MVP 范围

### 2.1 本阶段必须实现

#### 模型管理

- 新增模型
- 编辑模型
- 删除模型
- 启用或停用模型
- 测试连接

模型配置字段仅包含：

- `name`
- `provider`
- `baseUrl`
- `modelName`
- `apiKey`
- `enabled`

模型接入策略：

- MVP 第一版优先支持 OpenAI 兼容接口
- `Claude`、`Gemini`、`Grok`、`豆包`、`DeepSeek` 先预留 `provider` 类型
- 非 OpenAI 兼容 provider 不在本阶段落地

#### 聊天能力

- 单聊
- 多模型群聊
- 会话历史保存
- 重新打开历史会话继续聊天

#### 群聊规则

- 创建群聊时可选择多个模型
- 每个房间需要保存模型顺序
- 用户发送一条消息后，模型按固定顺序依次回复
- 后一个模型能看到前一个模型在当前轮中的已成功回复
- 本阶段不实现角色分工、`@` 打断、自动继续、多轮自动博弈

### 2.2 本阶段明确不做

以下内容全部留到后续版本，不得混入 MVP：

- 图片上传
- 文件解析
- 语音输入
- 语音播报
- Prompt 模板
- 超长 Prompt 导入
- 自动总结
- 搜索
- 归档
- 导出
- 成本统计页面
- 错误日志页面
- 角色分工
- `@` 打断
- 自动继续多轮
- 多端 App 或小程序
- 多用户
- 登录注册
- 商业化和权限系统

## 5. 数据模型规范

### 5.1 `model_configs`

用途：保存可供房间使用的模型配置。

字段：

- `id`
- `name`
- `provider`
- `base_url`
- `model_name`
- `api_key`
- `enabled`
- `created_at`
- `updated_at`

约束：

- `name` 在本地单用户场景下应保持唯一
- `enabled = false` 的模型不可用于新建房间
- `api_key` 仅服务端可见

### 5.2 `chat_rooms`

用途：保存会话房间。

字段：

- `id`
- `title`
- `type`，枚举值为 `single` 或 `group`
- `created_at`
- `updated_at`

约束：

- `single` 表示单聊房间
- `group` 表示群聊房间

### 5.3 `chat_room_models`

用途：保存房间与模型的关联关系及顺序。

字段：

- `id`
- `room_id`
- `model_id`
- `sort_order`

约束：

- `room_id + model_id` 必须唯一
- `room_id + sort_order` 必须唯一
- 单聊房间也必须写入本表
- 单聊房间必须且只能关联 1 个模型
- 群聊房间必须至少关联 2 个模型

### 5.4 `messages`

用途：保存聊天消息。

字段：

- `id`
- `room_id`
- `sequence`
- `role`，枚举值为 `user`、`assistant`、`system`
- `model_id`，可空；用户消息为空
- `content`
- `created_at`

约束：

- `room_id + sequence` 必须唯一
- 同一房间的消息顺序以 `sequence` 为准，不以时间戳推断
- 本阶段只保存纯文本消息

## 6. 接口范围

### 6.1 模型管理

- `GET /api/models`
- `POST /api/models`
- `PUT /api/models/:id`
- `DELETE /api/models/:id`
- `POST /api/models/:id/test`

### 6.2 会话管理

- `GET /api/rooms`
- `POST /api/rooms`
- `GET /api/rooms/:id/messages`
- `POST /api/rooms/:id/messages`

## 7. 消息流程规范

### 7.1 单聊流程

1. 用户进入单聊房间
2. 前端提交消息到 `POST /api/rooms/:id/messages`
3. 服务端保存用户消息
4. 服务端读取该房间唯一绑定的模型
5. 服务端调用模型接口
6. 服务端保存模型回复
7. 返回本轮新增消息给前端显示

### 7.2 多模型群聊流程

1. 用户发送消息
2. 服务端先保存用户消息
3. 服务端按 `sort_order` 依次调用房间中的模型
4. 每个模型读取当前房间历史消息，以及本轮前面模型的已成功回复
5. 每个模型成功返回后立即保存一条 `assistant` 消息
6. 全部执行完成后返回本轮新增消息

## 8. 失败处理规范

本阶段采用“降级继续”的失败策略：

- 用户消息必须先保存
- 模型顺序调用过程中，如某个模型失败或超时，则已成功保存的模型回复保留，不回滚
- 当前失败模型不生成消息
- 后续健康模型继续执行，房间按顺序降级完成本轮
- 接口返回“部分成功”结果，并带上失败模型标识、错误摘要以及本轮各模型结果

补充约束：

- “测试连接”失败不应写入聊天消息表
- 聊天接口不得因为单个模型失败而丢失本轮已保存消息

## 9. API Key 安全底线

虽然本阶段是本地单用户 MVP，仍必须满足以下规则：

- `api_key` 只允许服务端读取和使用
- 模型列表和详情接口不得回传明文 `api_key`
- 编辑模型时，如未提交新 `api_key`，应保留旧值
- 日志和报错信息不得打印明文 `api_key`
- 仓库中不得提交真实 `.env`
- 必须提供 `.env.example`

说明：

- 用户自行配置的模型密钥属于业务数据，应存于数据库
- 应用运行所需环境变量放入 `.env`

## 10. 目录建议

```text
app/
components/
server/
  adapters/
  orchestrators/
  services/
lib/
prisma/
types/
public/
```

目录职责：

- `app/`：页面和 API 路由入口
- `components/`：纯 UI 组件
- `server/adapters/`：模型调用适配层
- `server/orchestrators/`：多模型顺序编排
- `server/services/`：业务逻辑与数据协调
- `lib/`：通用工具、常量、错误处理、数据库客户端
- `prisma/`：数据库 schema 和 migration
- `types/`：项目共享类型

## 11. 最小实现原则

- 页面层不写复杂业务逻辑
- API Route 只做参数接收、参数校验、调用 service、返回响应
- 第三方模型调用必须统一收口到适配层
- 多模型顺序回复必须统一收口到编排层
- 不为了赶进度把多种职责直接写死在页面或 route 中

## 12. 最小测试与验收标准

### 12.1 自动化测试最低要求

至少覆盖以下场景：

- 模型连接测试可通过 mocked OpenAI 兼容接口完成校验
- 单聊发送消息后，能保存用户消息和模型回复
- 群聊发送消息后，模型按配置顺序回复
- 群聊中后一个模型可读取前一个模型本轮已成功回复
- 某个模型失败时，已成功回复保留，后续健康模型继续回复
- 刷新后可以重新读取历史消息

### 12.2 人工验收通过条件

满足以下条件即可视为 MVP 跑通：

- 页面能打开
- 模型可以新增、编辑、删除、启停
- 模型连接测试可成功返回结果
- 可以创建单聊和群聊
- 用户发送一句话后，多个模型能按顺序回复
- 刷新页面后聊天记录仍存在
- 历史会话可以重新打开继续聊天

## 17. 本地开发代理说明

如果本机开启了 TUN 模式代理，或设置了 `http_proxy` / `https_proxy`，本地开发时可能会把 `localhost` 也错误走代理，导致：

- `http://localhost:3000` 返回 `502`
- 浏览器或自动化工具访问本地页面持续超时

项目已提供本地开发启动脚本，会自动为当前进程补齐 `NO_PROXY`：

```bash
npm run dev:local
```

这个脚本会自动把以下地址加入绕过列表：

- `localhost`
- `127.0.0.1`
- `::1`

如果你仍然使用系统代理或 Clash / Mihomo 一类工具，建议同时在代理规则中将上述地址设置为 `DIRECT`，避免本地开发服务被代理劫持。
