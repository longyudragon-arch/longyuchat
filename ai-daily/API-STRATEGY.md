# AI 日报的大模型 API 策略

## 1. 是否一定要购买大模型 API？

结论：

- **写规划、搭页面、建数据表时，不需要**
- **真正跑“全自动日报生成”时，需要至少一个可用的大模型 API**

因为自动日报至少要做这些 LLM 任务：

- 价值打分
- 去噪筛选
- 聚类辅助
- 摘要生成
- 每期日报导语与条目正文生成

没有大模型 API，就只能做“纯聚合列表”，做不到你要的自动日报质量。

## 2. 是否需要“额外购买”？

不一定。

如果你现在已经有可用的模型 API（例如当前聊天模块正在使用的 OpenAI 兼容、Gemini、OpenRouter 等），那么：

- 可以直接复用
- 不需要单独为了日报再买一套新 API

如果你现在没有任何可用模型额度，那么：

- 至少需要开一个提供商账号
- 最好先从便宜且稳定的模型开始

## 3. 推荐提供商策略

### 第一阶段推荐

优先选一个低成本主模型：

- Gemini Flash / 同级低价模型
- OpenAI 兼容的低价模型
- OpenRouter 上的低价稳定模型

用于：

- 打分
- 过滤
- 摘要
- 初稿生成

### 第二阶段推荐

如果后续你发现日报质量不够，再加：

- 一个更强的生成模型作为最终成稿模型
- 一个更便宜的模型继续做初筛

也就是：

- 便宜模型做筛选
- 稍强模型做最终成稿

## 4. 推荐调用策略

建议分层调用：

- `score/filter model`
- `summary model`
- `editor model`

第一版也可以先全部共用一个模型，等跑通后再拆。

## 5. 与 LongyuChat 的关系

长期建议：

- AI 日报 worker 不自己硬编码 provider 细节
- 尽量复用 `LongyuChat` 现有的 provider / model 抽象思路

但第一版不建议强耦合到聊天室页面逻辑里。

更合理的是：

- 先独立用环境变量接一个模型
- 跑通后，再考虑让日报 worker 复用站内模型配置

## 6. 成本建议

第一版控制成本的关键不是“找最便宜模型”，而是：

- 缩小来源范围
- 做好去重
- 先打分再成稿
- 限制每天最终入选条目数

推荐策略：

- 小时级扫描时只做轻量打分
- 每日发布时只对高分 cluster 做正式生成

## 7. 当前建议

如果你只是准备开始做这个项目：

- **不用马上买贵模型**
- **但要准备至少一个可调用的 API**

如果你已经有聊天模块用的模型 key：

- 先复用它
- 后面再根据成本和质量拆专用日报模型
